
任何程序的 optimization，核心就是两个字：打满。打满计算资源、打满内存带宽，总之不要浪费就好了。

对于单核而言，这些优化通常包含向量化、优化内存访问、减少不必要计算等等。不作为重点来讲。

对于多核而言，主要是并行化技术。大概分成分解、分配、协调、实例化这几部分。其中实例化几乎完全由软硬件自动完成，分配和协调可以由软件完成一部分，分解大多需要人工完成。

## 分配

分配的最重要任务，是按照不同目标硬件的能力，分配合适数量的工作过去，使得所有硬件尽量同时完成工作。绝大多数情况，我们都希望平均分配。

既然想要平均分配，那么就要对工作量进行预判。判断越准，分配越好。

常用的分配方法有 static, dynamic。

dynamic 这里有一个 trade-off：随着你把 workload 分得更细，你能把工作更均匀地分配给各个 worker，但你也会有更大的 overhead。

分配方法需要考虑的另一个问题，就是尽量减少通信。

Cilk, ISPC

分配任务时需要考虑的另一个点，就是分配之后彼此是否容易协调。
## 协调

协调，其实是把通讯和同步合二为一来说了。

这是最麻烦、产生最多额外耗时的部分。

协调有好几种不同的方式。

第一种是 shared memory 模型，所有 worker 都能访问、修改同一块内存地址。此时的通信是隐式发生的，但也引入了竞争的问题。这需要使用锁、barrier 等等来解决。

第二种是 message passing 模型，每个 worker 看到的是自己私有的内存地址。此时的通信必须显式发生，一个 worker 发送某些消息，另一个 worker 显式接收它们。可以分成 synchronous, asynchronous 两类。

事实上，通讯是抽象的。不仅发生在不同 process 之间，还可以发生在不同 computer，以及 memory to cache, register to chip 等等，只不过我们一般忽略了这些通讯协议。

通讯可以分成两种，一种是 inherent 的，由算法的性质决定，是从理论上而言需要进行的；另一种是 artificial 的，由系统的性质决定，是由于具体系统实现导致的。第一类很好理解，第二类可以举些例子。比如 cache，由于受到 cache 大小的限制，如果我们访问顺序不恰当的话，就会导致重复的 memory to cache 搬运，这就很糟糕。

提到通讯，就不得不提到 bandwidth。其实一般而言我们不太在意 latency，因为我们几乎总有足够多的并行任务来掩盖 latency。一旦我们忽略掉 latency，也就是说假设 cpu 或者 memory 被足够多的任务打满了，那么就只有 bandwidth 是重要的。

但是，cpu 和 memory 谁会先成为瓶颈呢？这就需要看一下我们问题对应的算术强度了。得到算术强度，我们从 roofline model 中就能看出当前是什么瓶颈、该如何优化。

首先看出是 memory bound 或者 computation bound 是容易的，无非就是在 roofline 的不同区域罢了。这个时候，因为是 throughput bound，我们的主要优化思路就是提高算术强度，通常而言是通过减少通讯，也就是重新设计算法，或者改变顺序等等。

那如果我们在 roofline 下面呢？说明 cpu/memory 不是在每一时刻都跑着有用的东西。有可能是因为 overhead 在算奇怪东西，有可能是因为 latency 在空转。那就对应优化好了。
